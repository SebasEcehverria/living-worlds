## Project Overview

Living Worlds is an AI-powered fantasy adventure game built using the MERN stack (MongoDB, Express, React, and Node.js).

Players will explore a small fantasy village, interact with AI-powered NPCs (non-player characters), collect items, and complete quests.

The main feature is an AI-powered conversation system. Instead of having NPCs repeat predefined dialogue, players can type messages and receive responses generated by Jetstream2's hosted Qwen language model.

Each NPC will have a unique personality and will receive relevant context about the player and the game world.

The goal is to build a small, fully functional game before expanding it with additional features.

# CS333 Final Project Plan

## Part 1: What It Is and Who It's For

### What is your app? What will it do?

Living Worlds is a small fantasy adventure game where players can explore a village, interact with characters, and complete a simple quest.

Players will be able to select NPCs and have conversations using an AI chat interface powered by Jetstream2's Qwen model.

The game will keep track of the player's inventory, quest progress, and conversations using MongoDB.

React will handle the user interface, Express will manage the backend and API requests, and Qwen will generate dialogue based on each NPC's personality and relevant game context.

The initial game will contain one village, three NPCs, and one quest.

### Who will use it?

The intended users are people who enjoy fantasy RPGs, interactive storytelling, and AI-powered games.

When users open the app, they should be able to start an adventure, interact with villagers, discover information through dialogue, and make progress toward completing a quest.

The goal is to make the characters feel more interactive than traditional NPCs with predefined dialogue.

## Part 2: What Can People Do With It?

The three starred features are essential and will be developed first.

1. ⭐ **Start and save an adventure:** Create a new game, save progress, and continue a previous game.
2. ⭐ **Talk to AI-powered NPCs:** Select a character, type messages, and receive AI-generated dialogue.
3. ⭐ **Manage inventory and complete a quest:** Collect items, view inventory, and complete a simple quest.
4. **Explore a fantasy village:** View an illustrated village map and select different NPCs.
5. **Track quest progress:** View the current objective and completion status.
6. **Review conversation history:** View previous conversations with NPCs.
7. **Reset game progress:** Delete a saved game and start over.
8. **NPC memory:** Characters can reference relevant previous conversations and completed quests.

### Minimum Viable Product (MVP)

The initial completed application will include:

- One village map with clickable NPCs.
- Three NPCs with different personalities.
- A working AI conversation interface.
- One completable quest.
- A basic inventory system.
- MongoDB database storage.
- Working create, read, update, and delete functionality.
- Save and load functionality.

Advanced features such as character movement, additional locations, combat, and automatically generated quests will not be required for the first version.

## Part 4: Data and MongoDB Collections

The application will use MongoDB and Mongoose to store game information.

### Collection: `gameSaves`

Stores player progress.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Automatic | Unique game save ID |
| `playerName` | String | Yes | Player name |
| `location` | String | Yes | Current location; defaults to `village` |
| `inventory` | Array of ObjectIds | No | References to collected items |
| `questStatus` | String | Yes | `not_started`, `active`, or `completed` |
| `createdAt` | Date | Yes | Save creation date |
| `updatedAt` | Date | Yes | Last save update |

For the MVP, the game will have one quest, so its progress can be stored directly in the saved game.

### Collection: `npcs`

Stores NPC character information.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Automatic | Unique NPC ID |
| `name` | String | Yes | Character name |
| `personality` | String | Yes | Character personality |
| `description` | String | No | Character background |
| `location` | String | Yes | NPC location |
| `systemPrompt` | String | Yes | AI personality instructions |

The initial game will contain three NPCs:

**Garrick — The Merchant**

A cautious merchant who is suspicious of strangers but willing to help.

**Lyra — The Ranger**

A forest ranger who knows the wilderness surrounding the village.

**Elden — The Scholar**

A curious scholar interested in ancient ruins and mysterious discoveries.

Each NPC will have a predefined personality and background information that will be included in requests to Qwen.

### Collection: `items`

Stores available game items.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Automatic | Unique item ID |
| `name` | String | Yes | Item name |
| `description` | String | No | Item description |
| `type` | String | Yes | Item category |
| `questItem` | Boolean | No | Whether the item is needed for a quest |

### Collection: `conversations`

Stores conversations between players and NPCs.

| Field | Type | Required | Description |
|---|---|---|---|
| `_id` | ObjectId | Automatic | Unique conversation ID |
| `gameSaveId` | ObjectId | Yes | Reference to the saved game |
| `npcId` | ObjectId | Yes | Reference to the NPC |
| `messages` | Array | No | Embedded conversation messages |

Each embedded message contains:

| Field | Type | Required |
|---|---|---|
| `role` | String | Yes |
| `content` | String | Yes |
| `timestamp` | Date | Yes |

The `role` field will contain either `user` or `assistant`.

### Data Relationships

- One game save can have multiple NPC conversations.
- Each conversation belongs to one NPC and one game save.
- Conversation messages are embedded inside the conversation document.
- A game save references collected items.
- NPCs and items will initially be created using seed data.

The browser will use localStorage to remember the active game save ID. MongoDB will store the actual game progress.

## Part 5: API Routes

The backend will use Node.js and Express to provide the following API routes.

| Method | Route | Description |
|---|---|---|
| GET | `/api/health` | Check whether the backend is running |
| POST | `/api/saves` | Create a new saved game |
| GET | `/api/saves/:id` | Retrieve saved game progress |
| PUT | `/api/saves/:id` | Update saved game progress |
| DELETE | `/api/saves/:id` | Delete a saved game and its conversations |
| GET | `/api/npcs` | Retrieve all NPCs |
| GET | `/api/npcs/:id` | Retrieve a specific NPC |
| GET | `/api/items` | Retrieve available items |
| GET | `/api/conversations/:saveId/:npcId` | Retrieve conversation history |
| POST | `/api/conversations/:saveId/:npcId/messages` | Send a message and generate an AI response |
| DELETE | `/api/conversations/:saveId/:npcId` | Delete conversation history |

### CRUD Operations

The application will demonstrate all four required database operations.

**Create:**
- Create a new game save.
- Save new conversation messages.

**Read:**
- Retrieve saved games.
- Retrieve NPC information.
- Retrieve inventory items.
- Retrieve conversation history.

**Update:**
- Update player progress.
- Update inventory.
- Update quest status.

**Delete:**
- Delete saved games.
- Clear conversation history.

### AI Conversation Request Flow

1. Player enters a message in the React chat interface.
2. React sends the message to the Express backend.
3. Express retrieves the NPC's personality and relevant game information from MongoDB.
4. Express sends the message and context to Jetstream2's hosted Qwen API.
5. Qwen generates an NPC response.
6. Express saves the conversation in MongoDB.
7. React displays the generated response to the player.

The Express backend will also enforce rate limiting and input validation.

### Game State Validation

The AI will only generate dialogue.

It will not directly modify:

- Player inventory.
- Quest completion.
- Saved progress.
- Game locations.

The Express backend will validate updates to these fields.

This prevents AI responses from accidentally changing game state or awarding items that do not exist.

## Part 8: The Hardest Part

### What part am I most worried about?

The most challenging part will likely be implementing AI-powered NPC conversations while keeping the characters consistent with their personalities and the current game state.

Since the AI generates responses dynamically, it might occasionally forget information, invent details, or contradict the game's rules.

I also need to ensure that the React frontend, Express backend, MongoDB database, and Jetstream2 Qwen API communicate correctly.

### How will I address this?

I will separate AI-generated dialogue from the actual game logic.

MongoDB and Express will manage important information such as:

- Inventory.
- Quest progress.
- Completed objectives.
- NPC information.
- Conversation history.

When a player sends a message, the backend will provide Qwen with the NPC's personality and relevant game information.

The AI will generate dialogue but will not directly control gameplay actions.

### Backup Plan

If the Qwen API is unavailable or AI integration becomes too complicated, the application will use predefined dialogue for NPC conversations.

Players will still be able to:

- Explore the village.
- Select characters.
- View dialogue.
- Collect items.
- Complete the quest.
- Save and load progress.

If implementing a more interactive village becomes too difficult, the game will use a static illustrated map with clickable NPCs.

The goal is to finish a smaller working application rather than an unfinished project with too many features.
